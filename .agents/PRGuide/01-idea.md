# 01 — Idea Honing (raw Q&A log)

This is a running log. Questions and answers are appended in order as they
happen. Not refactored into a summary — the log is the deliverable.

## Q1 (kickoff): Does something like this already exist, or do we build it?

**A (2026-10-12):** Build. Prior art covers pieces but not the whole loop:
Devin Review (orders/groups hunks, web UI, hosted agent), ai-pr-review
(narrated walkthrough in a browser), tuicr (terminal diff review whose
comments flow back to the agent via a tmux split, no narrative), CodeRabbit
walkthroughs (layered summary as a static PR comment), prwalk (per-chunk
accept/reject in a browser) and DiffDeck (browser diff, comments sent to the
agent). The gap is: an ordered call-chain narrative as terminal slides,
generated by the user's own agent through a skill, with comment triage
(the agent answers, or the comment goes to the PR author).

Ideas raised at kickoff, not yet decided:
- The guide file references diff hunks rather than copying diff text; the
  CLI renders the real diff from git and detects stale slides.
- A deterministic coverage check: every hunk in the PR appears on some
  slide, or on an automatic "not covered" slide.
- Comment loop: the viewer writes comments to a file; the agent runs a
  blocking `wait` command; the agent answers itself or drafts a question for
  the PR author, with human approval before anything is posted.

## Q2 (kickoff): What is the tool called?

**A (2026-10-21):** `prguide`. It was free on npm, crates.io, PyPI and
Homebrew, and no real GitHub project used the name. Repo:
https://github.com/itsypkin/PRGuide

## Q3 (kickoff): What is the binary called?

**A (2026-10-21):** Ship two names for the same binary. `prg` is the short
command for humans. `prguide` is the full name, and the skill always calls
that one, because the agent's shell loads the user's aliases and some users
already have `alias prg=...`. The package is published as `prguide`
(`prg` is taken on npm and PyPI).

## Q4: Whose PRs will prguide mainly be used to review?

Options offered: teammates' PRs (author questions become GitHub PR
comments); my own coding agent's PRs (author questions go back to that
agent); both.

**A (2026-10-21):** Both, equally. Both cases are first-class in v1, and
where an author question goes depends on who the author is.

## Q5: What can prguide review in v1?

Options offered: GitHub PRs plus local branches; GitHub PRs only; PRs,
branches and uncommitted working-tree changes.

**A (2026-10-21):** GitHub PRs only. Your own agent opens a (draft) PR
before you review it, so a comment always has a PR to land on. Local
branches and working-tree changes are out of scope for v1.

## Q6: When the author is your own coding agent, how does an "ask the author" comment reach it?

Options offered: always a PR comment; a PR comment plus a direct hand-off
to a live agent pane; the reviewer chooses per comment.

**A (2026-10-21):** Always a PR comment. Every author gets the same path.
prguide never talks to other agents directly. A coding agent (or a
ChocoFactory loop) picks the comment up like any other review comment.

## Q7: How much approval before a comment is posted to GitHub under the reviewer's account?

Options offered: approve the batch; approve each comment; no approval.

**A (2026-10-21):** Approve the batch. The agent drafts all author
questions. The reviewer sees the list, can edit or drop any of them, and
then posts them once as a single PR review.

## Q8: When the agent answers a comment itself, where does the answer go?

Options offered: local, with an option to promote; local only; always
posted on the PR too.

**A (2026-10-21):** Local, can promote. The answer shows under the
reviewer's comment in the viewer only. The reviewer can mark it "post
anyway", for example to put it on the record or because they don't trust
the answer. A promoted item joins the batch from Q7.

## Q9: Which agent harnesses must the skill support in v1?

Options offered: agent-agnostic; Claude Code only; prguide runs the agent
itself (`claude -p` / codex) with no skill.

**A (2026-10-21):** Agent-agnostic. One SKILL.md, and a CLI plain enough
for any agent (Claude Code, Codex, pi/omp...). Test on Claude Code and
Codex. All the agent intelligence lives in the skill and none in the
binary: prguide never calls a model itself.

## Q10: Implementation language?

Options offered: Rust (ratatui); Go (bubbletea); TypeScript (Ink).

**A (2026-10-21):** Rust with ratatui. A single static binary on the same
stack as ChocoFactory, distributed via cargo, brew and GitHub release
binaries.

## Q11: When does the agent see the reviewer's comments?

Options offered: live, as you write; at the end of the deck; whenever the
reviewer presses "send".

**A (2026-10-21):** Live, as you write. Each comment goes to the agent as
soon as it is saved, and the answer appears in the viewer while the
reviewer keeps reading, like asking the engineer next to you. This means
the agent stays in a listening loop for the whole review session (wait for
a comment → triage and answer → wait again).

## Q12: After the agent answers, can the reviewer reply and keep the conversation going?

Options offered: yes, threads; one answer per comment.

**A (2026-10-21):** Yes, threads. Each comment is a thread. The reviewer
can push back, and the agent replies again. Either side can turn the thread
into an author question, which then goes through the batch approval from
Q7.

## Q13: Is the guide agent only a narrator, or also a reviewer that flags problems?

Options offered: narrator plus flags on the slides; narrator only; a neutral
narrative with a separate findings slide at the end.

**A (2026-10-21):** Narrator plus flags. The agent explains the change and
also marks the spots worth a closer look right on the relevant slide (for
example "no test for this branch" or "this changes behaviour for X"). The
reviewer still decides everything; a flag is not a verdict.

## Q14: After new commits are pushed, what does a second review look like?

Options offered: a delta guide covering only what changed; regenerate the
whole guide; not in v1 (pinned to a commit, with a "PR moved on" warning).

**A (2026-10-21), owner's words:** "I think we need both, a user might want
to see the whole guide, if they join the discussion after the latest commit
is pushed but also they should be able to see the changes in the latest
commit"

So both are needed: a full guide for the current head (for someone joining
late) and a delta view of what the latest push changed (for someone who
already reviewed). "Joining the discussion" also raises whether a guide is
shared between reviewers → Q15.

## Q15: Is a guide personal to one reviewer, or shared with others?

Options offered: shared via the PR; personal and local; personal now,
shared later.

**A (2026-10-21):** Personal now, shared later. In v1 each reviewer's agent
makes its own guide on their machine, and "joining late" means generating
the full guide for the current head. The guide format must be designed so
it can be published later without changes (for example, no absolute local
paths and no machine-specific state inside the guide itself).

## Q16: What is the delta view measured against?

Options offered: my last guide's commit; the latest push only.

**A (2026-10-21), owner's words:** "we should have some UI that would allow
the user to say for which commits to generate the guide (if they don't want
to have a full one) and then the guide is generated against the other
changes in the PR, basically the idea here is to show this is what has
happened in this commits"

So the delta is not a fixed rule. The reviewer picks a set of commits in a
UI, and the guide explains what those commits did, in the context of the
rest of the PR. A full guide is the same thing with every commit selected.

## Q17: Where does the commit picker live?

Options offered: in the prg viewer; in the agent's chat; both.

**A (2026-10-21):** In the prg viewer. prg lists the PR's commits, the
reviewer selects a range and presses "generate", and the request reaches
the listening agent through the same channel as comments. The new guide
opens when it is ready.

### Q17 follow-up (owner, 2026-10-21)

> perhaps the agent also should be able to select the commit range via cli

So the commit range has two entry points: the prg viewer's picker (the
main one for humans) and a `prguide` CLI option the agent can use, for
example when the reviewer asks in chat ("guide me through the last two
commits"). Both lead to the same kind of guide.

## Q18: How does a review session start, and who opens the viewer pane?

Options offered: the agent opens it; the reviewer opens it; viewer first
(the reviewer runs prg, and it asks an already-listening agent to generate).

**A (2026-10-21):** The agent opens it. The reviewer runs the skill (for
example "/prguide 1234"). The agent writes the guide, opens `prg` in a new
herdr/tmux pane if it is running in one (otherwise it prints the command
for the reviewer to run), and then starts listening.

## Q19: How strict should prguide be about the guide covering every changed hunk?

Options offered: strict, with a bulk slide for mechanical changes; an
automatic "not covered" slide plus a coverage percentage; no check.

**A (2026-10-21):** No check. prguide trusts the agent to choose what goes
in the guide. (Raised at kickoff: a convincing story can leave out the hunk
that matters. The owner accepts this for v1.)

## Q20: Can slides show code the PR didn't change, when the call chain passes through it?

Options offered: yes, marked as context; diff hunks only.

**A (2026-10-21):** Yes, marked as context. A slide can include snippets of
unchanged code from the PR's head commit (file + line range), visually
marked as unchanged, next to the diff hunks.

## Q21: What can a comment be attached to?

Options offered: a line, a line range, or the whole slide; the whole slide
only.

**A (2026-10-21):** Lines or the whole slide. The reviewer can select a line
or range in a hunk, or comment on the slide as a whole. When posted, line
comments become inline review comments on that line, and slide comments go
in the review body. (A note for design: GitHub only accepts inline comments
on lines in the diff, so a comment on an unchanged context snippet from Q20
has to go in the review body, quoting the code.)

## Q22: How is the architecture sketch slide drawn?

Options offered: the agent draws text art; the agent writes Mermaid and prg
draws it as text; Mermaid as the main format with a text-art fallback.

**A (2026-10-21):** Mermaid, with a text fallback. The agent writes Mermaid,
and prg draws it with box characters. When prg can't draw a diagram (an
unsupported type, or a render failure), it shows the agent's text-art
version instead. Candidate research topic: what Mermaid-to-terminal
renderers exist that a Rust binary can use, and which diagram types they
support.

## Q23: How does prguide get the PR's code locally?

Options offered: a worktree created from the local clone; fetch the refs
only and read through git; auto-clone into a cache dir when not in a clone.

**A (2026-10-21):** A worktree from a clone. prguide runs inside the
reviewer's local clone, fetches the PR head, and creates a separate git
worktree for it, so the reviewer's own working tree and branch are never
touched. Running outside a clone of the PR's repo is an error in v1.

## Q24: Can prg submit a review verdict along with the batch?

Options offered: yes (Comment / Approve / Request changes); comment only.

**A (2026-10-21):** Comment only. prg posts the batch as a review with the
"Comment" event. The reviewer approves or requests changes on GitHub
themselves, so prguide can never approve a PR.

## Q25: Does prg show the PR's existing GitHub threads, and the author's replies to posted questions?

Options offered: both, read-only; only replies to my posted questions;
neither.

**A (2026-10-21):** Both, read-only. Existing PR review threads and the
replies to questions the reviewer posted appear on the matching slide or
line, marked as coming from GitHub. The reviewer replies on GitHub, not in
prg. The agent can read these threads as context when it answers.

## Q26: Which topics get a Step 2 research doc?

Options offered: the live agent loop; Mermaid in the terminal; the GitHub
review API; opening panes in herdr/tmux.

**A (2026-10-21):** The live agent loop and Mermaid in the terminal. The
GitHub review API and pane opening are left to the design phase.

The owner added a new idea with this answer, in their words:

> I have one more idea that I want you to encorporate, I want an agent to be able to insert a slide as an explanation to the human question, basically the initial slides a novigated with up/down arrows, but then a user can ask "how this thing work" and the agent can create a slide to the left of the current one with deep dive into the the topic and prg draws it so customer can navigate to it for detailed explanation

So the deck is two-dimensional. The main guide is navigated with up/down.
When the reviewer asks a question such as "how does this thing work?", the
agent can create a deep-dive slide attached to the current slide, placed to
its left. prg shows it live, and the reviewer navigates left to read it.

## Q27: What shape do multiple deep dives take?

Options offered: a row to the left with no nesting; a tree; one deep dive
per slide, extended over time.

**A (2026-10-21), owner's words:** "One per slide for now, later we can
consider if this should be more complicated if so we will go with the tree
option"

So in v1 each slide has at most one deep dive, and the agent adds sections
to it when the reviewer asks more. If this grows later, the next step is
the tree. The format should not rule a tree out.

## Q28: Who decides that a question gets a deep-dive slide instead of a thread reply?

Options offered: the agent decides and the reviewer can also ask; only an
explicit "deep dive" action; the agent always decides.

**A (2026-10-21):** The agent decides, and the reviewer can also ask. The
agent chooses between a thread reply and a deep dive based on the question.
The reviewer can force a deep dive with a "deep dive" action on a comment.
